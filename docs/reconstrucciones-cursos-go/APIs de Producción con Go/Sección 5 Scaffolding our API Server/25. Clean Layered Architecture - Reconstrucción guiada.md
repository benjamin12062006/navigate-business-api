## Objetivo de la lección

Diseñar la aplicación alrededor de límites comprensibles antes de añadir código: el transporte interpreta HTTP, la lógica coordina reglas y el almacenamiento oculta los detalles de persistencia.

## Estado inicial heredado

La lección parte del servidor HTTP presentado previamente. No incorpora todavía implementaciones completas de base de datos, correo, autenticación o rate limiting.

## Fase 1 — Dibujar el recorrido de una petición

Procedencia: E1, E2.

```text
cliente → router/mux → handler HTTP → lógica de aplicación → store → base de datos
```

La dependencia avanza en una sola dirección. El handler no conoce SQL y el store no conoce HTTP.

## Fase 2 — Expresar las dependencias como contratos

Procedencia: E1, E3.

```go
package app

import "context"

type User struct {
	ID    int64
	Email string
}

type Store interface {
	UserByID(ctx context.Context, id int64) (*User, error)
}

type Mailer interface {
	Send(ctx context.Context, to, subject, body string) error
}

type Authenticator interface {
	GenerateToken(userID int64) (string, error)
}
```

Los nombres son una reconstrucción representativa. Lo respaldado directamente es que la aplicación depende de interfaces para almacenamiento, correo, autenticación y rate limiting.

## Fase 3 — Componer en una estructura de aplicación

Procedencia: E3.

```go
package app

import "log/slog"

type Application struct {
	Logger        *slog.Logger
	Store         Store
	Mailer        Mailer
	Authenticator Authenticator
}

func NewApplication(
	logger *slog.Logger,
	store Store,
	mailer Mailer,
	authenticator Authenticator,
) *Application {
	return &Application{
		Logger:        logger,
		Store:         store,
		Mailer:        mailer,
		Authenticator: authenticator,
	}
}
```

## Fase 4 — Posponer una capa que todavía no aporta valor

Procedencia: E4.

El instructor explica que una capa de servicio es útil para orquestación, pero decide no imponerla todavía. Las transacciones compuestas permanecen en el almacenamiento mientras las operaciones auxiliares solo se usen allí. La decisión puede cambiar cuando aparezca lógica reutilizable.

## Código final completo de la lección

El estado reconstruible es el contrato y la composición mostrados en las fases 2 y 3. No se atribuye al curso un árbol de archivos exacto que la transcripción no conserva.

## Conceptos fundamentales

- Separar por responsabilidad, no por moda arquitectónica.
- Inyectar interfaces donde una dependencia deba sustituirse.
- Mantener el punto de composición cerca del arranque.
- Añadir la capa de servicio cuando exista orquestación real.

## Resumen mental

El objetivo no es acumular carpetas: es poder cambiar almacenamiento, correo o autenticación sin reescribir los handlers ni mezclar SQL con HTTP.
