## Objetivo de la lección

Elegir autenticación por necesidad y comprender qué propiedades se aceptan antes de escribir middleware.

## Fase 1 — Separar tres opciones

Procedencia: E1-E4.

| Opción | Estado | Ventaja | Riesgo o coste | Uso descrito |
|---|---|---|---|---|
| Basic auth | credenciales en cada petición | muy simple | UX pobre y verificación repetida | health, métricas o documentación privada |
| Token stateful | token persistido | revocación y control central | consulta al almacenamiento | aplicaciones que necesitan invalidación inmediata |
| JWT stateless | sin registro central del token | validación local y comunicación entre sistemas | claims obsoletos y revocación difícil | backend que sirve clientes y no necesita control fino del token |
| OAuth | identidad en tercero | reduce manejo directo de credenciales | dependencia del proveedor | acceso rápido con Google/GitHub u organizaciones integradas |

## Fase 2 — Flujo común de token

Procedencia: E2.

```text
credenciales → validación única → emisión con expiración
→ Authorization: Bearer <token> → validación → usuario autenticado
```

## Fase 3 — Regla sobre claims

Procedencia: E3.

No colocar en un JWT datos que puedan quedar obsoletos, como permisos o roles, salvo que el sistema acepte explícitamente esa ventana de inconsistencia. La guía del curso prefiere un identificador de usuario y recuperar el estado vigente del sistema.

## Fase 4 — Decisión del curso

Procedencia: E5.

El curso usa basic auth para superficies operativas y JWT stateless para la API principal. La elección de JWT es educativa y por interoperabilidad; no se presenta como solución universal. El contrato del autenticador debe permitir otra implementación.

## Resumen mental

Autenticar no es “poner JWT”: primero se decide quién controla el estado, cómo se revoca, qué datos pueden caducar y qué dependencia externa se acepta.
