## Objetivo de la lección

Materializar el repository pattern como un agrupador de repositorios de dominio sin esconder que cada uno sigue siendo una interfaz.

## Fase 1 — Contratos agrupados

Procedencia: E1.

```go
package store

import "context"

type Post struct{ ID int64 }
type User struct{ ID int64 }

type Posts interface {
	Create(ctx context.Context, post *Post) error
}

type Users interface {
	Create(ctx context.Context, user *User) error
}

type Storage struct {
	Posts Posts
	Users Users
}
```

## Fase 2 — Implementaciones SQL

Procedencia: E2.

```go
package store

import (
	"context"
	"database/sql"
)

type PostStore struct{ db *sql.DB }

func (s *PostStore) Create(ctx context.Context, post *Post) error {
	return nil // La consulta se implementa en la lección siguiente.
}

type UserStore struct{ db *sql.DB }

func (s *UserStore) Create(ctx context.Context, user *User) error {
	return nil // La consulta se implementa en la lección siguiente.
}

func NewStorage(db *sql.DB) Storage {
	return Storage{
		Posts: &PostStore{db: db},
		Users: &UserStore{db: db},
	}
}
```

## Fase 3 — Inyectar una sola dependencia compuesta

Procedencia: E3.

```go
type Application struct {
	store store.Storage
}

storage := store.NewStorage(db)
app := &Application{store: storage}
```

Un handler puede llamar `app.store.Posts.Create(ctx, post)` sin conocer `*sql.DB`.

## Código final completo de la lección

Los bloques anteriores son el estado final reconstruido. Los métodos devuelven `nil` deliberadamente porque esta lección crea el armazón; la persistencia real llega después.

## Decisión y coste

El agrupador produce una API cómoda, pero acopla la composición de repositorios en una estructura. La lección hace explícito ese intercambio y prefiere simplicidad porque el proyecto ya eligió PostgreSQL.

## Resumen mental

La interfaz se conserva en cada capacidad (`Posts`, `Users`); `Storage` solo las agrupa y `NewStorage` decide qué implementaciones concretas reciben la conexión.
