## Objetivo de la lección

Ocultar la tecnología de persistencia detrás de operaciones que expresen lo que la aplicación necesita.

## Fase 1 — Mostrar el acoplamiento que se elimina

Procedencia: E1.

```go
// Acoplado: quien llama debe conocer *sql.DB.
func getUserByID(ctx context.Context, db *sql.DB, id int64) (*User, error)
```

## Fase 2 — Introducir el contrato

Procedencia: E2.

```go
type Store interface {
	UserByID(ctx context.Context, id int64) (*User, error)
}

type Application struct {
	store Store
}

func NewApplication(store Store) *Application {
	return &Application{store: store}
}
```

## Fase 3 — Implementaciones sustituibles

Procedencia: E2, E3.

```go
type PostgresUserRepository struct {
	db *sql.DB
}

func (r *PostgresUserRepository) UserByID(ctx context.Context, id int64) (*User, error) {
	var user User
	err := r.db.QueryRowContext(ctx, `SELECT id, email FROM users WHERE id = $1`, id).
		Scan(&user.ID, &user.Email)
	return &user, err
}

type InMemoryUserRepository struct {
	users map[int64]*User
}

func (r *InMemoryUserRepository) UserByID(_ context.Context, id int64) (*User, error) {
	user, ok := r.users[id]
	if !ok {
		return nil, sql.ErrNoRows
	}
	return user, nil
}
```

## Fase 4 — Elegir la implementación en el arranque

Procedencia: E2.

```go
store := &PostgresUserRepository{db: db}
app := NewApplication(store)
```

Para una comprobación aislada se puede construir `Application` con `InMemoryUserRepository` sin abrir una conexión real.

## Código final completo de la lección

Los bloques de las fases 2 y 3 reconstruyen el contrato y las dos implementaciones descritas. Los nombres concretos pueden diferir del material visual; el mecanismo y sus firmas esenciales están respaldados.

## Resumen mental

El cambio de base de datos es una métrica de desacoplamiento, no necesariamente un requisito de negocio. El beneficio inmediato es separar responsabilidades y controlar dependencias.
