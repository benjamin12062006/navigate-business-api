## Mapa de procedencia

| ID | Pasaje | Evidencia recuperada |
|---|---|---|
| E1 | líneas 13-21; buscar `CREATE TABLE` | tabla `roles` y filas user/moderator/admin |

## Objetivo de la lección

Introducir roles en una base con datos existentes sin borrar usuarios ni dejar un default permanente frágil.

## Fase 1 — Crear catálogo de roles

Procedencia: E1.

```sql
CREATE TABLE IF NOT EXISTS roles (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(55) NOT NULL UNIQUE,
    level INTEGER NOT NULL DEFAULT 0,
    description TEXT
);

INSERT INTO roles (name, level, description) VALUES
    ('user', 1, 'Can create posts and comments'),
    ('moderator', 2, 'Can update other users posts'),
    ('admin', 3, 'Can update and delete other users posts');
```

## Fase 2 — Migrar usuarios existentes

Procedencia: E2.

```sql
ALTER TABLE users ADD COLUMN role_id BIGINT;

UPDATE users
SET role_id = (SELECT id FROM roles WHERE name = 'user');

ALTER TABLE users ALTER COLUMN role_id SET NOT NULL;
ALTER TABLE users
ADD CONSTRAINT users_role_id_fkey
FOREIGN KEY (role_id) REFERENCES roles(id);
```

La reconstrucción separa las operaciones para hacer explícito el orden que describe la clase. El SQL exacto de la constraint puede variar según la migración usada por el curso.

## Fase 3 — Reversión

```sql
ALTER TABLE users DROP CONSTRAINT IF EXISTS users_role_id_fkey;
ALTER TABLE users DROP COLUMN IF EXISTS role_id;
DROP TABLE IF EXISTS roles;
```

## Código final completo de la lección

Los tres bloques SQL son el estado reconstruido. El principio esencial es resolver la role por `name`, actualizar los registros y solo entonces imponer `NOT NULL`.

## Resumen mental

Una migración de producción debe transformar los datos existentes antes de endurecer el esquema. No se asume que `user` tenga siempre ID 1.
