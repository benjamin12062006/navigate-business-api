| E1 | líneas 13-17; buscar `role ID` | `CreateAndInvite` quedó roto al hacerse obligatorio `role_id` |

| E3 | líneas 23-27; buscar `admin` | permitir roles internos explícitos, pero nunca aceptar autoselección pública |

## Objetivo de la lección

Reparar la creación de usuarios sin codificar `role_id = 1` ni permitir escalamiento de privilegios desde el payload público.

## Fase 1 — Default de dominio

Procedencia: E2.

```go
func roleName(user *User) string {
	if user.Role.Name == "" {
		return "user"
	}
	return user.Role.Name
}
```

## Fase 2 — Resolver el ID en SQL

Procedencia: E1, E2.

```go
func (s *UserStore) create(ctx context.Context, tx *sql.Tx, user *User) error {
	return tx.QueryRowContext(ctx, `
		INSERT INTO users (username, email, password, role_id)
		VALUES ($1, $2, $3, (SELECT id FROM roles WHERE name = $4))
		RETURNING id
	`, user.Username, user.Email, user.Password.Hash, roleName(user)).Scan(&user.ID)
}
```

## Fase 3 — Mantener la elección fuera del registro público

Procedencia: E3.

```go
user := &User{
	Username: payload.Username,
	Email:    payload.Email,
	Role:     Role{Name: "user"},
}
```

Una herramienta interna o seed puede construir deliberadamente `Role{Name: "admin"}`. El endpoint público no copia un rol enviado por el cliente.

## Código final completo de la lección

Los tres bloques anteriores representan la corrección final. Si un rol interno no existe, la operación debe fallar como error de configuración o integridad; no convertirse silenciosamente en otro rol privilegiado.

## Resumen mental

Los identificadores de base no son reglas de negocio. El nombre estable `user` expresa la intención y evita depender de la secuencia de IDs.
